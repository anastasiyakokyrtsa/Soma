# Форма находки и правила аудита

## Форма находки

Каждая находка в `docs/state/findings.md`:

| Поле | Требование |
|---|---|
| № | Сквозная нумерация |
| Роль | Кто нашёл |
| Сценарий | К какому относится |
| Что не так | Одно предложение, конкретно |
| К чему приведёт | Последствие для человека или для бизнеса |
| Серьёзность | Блокер / высокая / средняя / низкая |
| Что сделать | Конкретное действие, а не направление мысли |
| Зависит от | Другая находка или нерешённый вопрос, если есть |

**Находка без поля «что сделать» отклоняется.** Это мнение, а не находка.

## Серьёзность

- **Блокер** — отказ при ревью в сторе, юридический риск, или человек не
  может пройти основной сценарий
- **Высокая** — человек бросит продукт в первую неделю
- **Средняя** — трение, потеря части аудитории
- **Низкая** — улучшение, можно отложить

## Что обязательно есть в отчёте

1. Раздел «что уже хорошо», заполненный содержательно. Аудит, нашедший
   только проблемы, — повод усомниться в глубине прохода, а не радоваться.
2. Раздел «что требует решения владельца продукта» — вопросы, которые
   роли не имеют права решить сами.
3. Рекомендуемый порядок правок с обоснованием порядка.

## Ограничение объёма

Не больше двадцати находок. Если больше — роли начали проектировать свой
продукт вместо аудита существующего. Сведи, объедини дубли, отсеки низкую
серьёзность.

## Правило приёмки находки

Перед включением в отчёт находку читает `audit-qa`:
- есть конкретное действие
- указано последствие
- не дублирует другую находку под иной формулировкой
- серьёзность обоснована, а не поставлена по ощущению
